# Phase 10 — freezing the contract at v1.0

The production-readiness roadmap (`docs/superpowers/plans/2026-07-24-production-readiness.md`) ends at Phase 8, and all three of its v1.0 exit criteria were met before Phase 9. Phase 9 cleared the debt list. Exactly one thing is left: decide what 1.0 means, then freeze it.

This phase **does not publish**: no release workflow, no CHANGELOG, no tag, no `prepublishOnly`. It also **ships no features** — if it ships a capability, it has failed.

Baseline: `main` @ `b52b269`, CI green on all five jobs (run 30801099127). Gate at that head, controller-verified from a deleted `dist/`: 1363/1363 tests (92 files), coverage 94.46/84.84/98.22/94.46 against the 90/80/95/90 floor, secret scan over 335 files, `smoke:package` green.

## Why bumping the version is not a one-line edit

This is the finding that shapes the whole phase, measured directly from the code rather than assumed.

`src/installer/manifest.ts` gates compatibility in two layers:

```ts
export const runtimeCompatibility = ">=0.1.0 <1.0.0";

export function isRuntimeCompatible(version: string, range = runtimeCompatibility): boolean {
  if (range !== runtimeCompatibility) return false;
  return /^0\.[1-9]\d*\.\d+(?:-[0-9A-Za-z.-]+)?$/.test(version);
}
```

The regex hard-refuses every 1.x version. So if `runtimeVersion` becomes `"1.0.0"` with nothing else changed, the following paths break:

| Path | Location | Consequence |
|---|---|---|
| `qa-skill runtime verify` | `program.ts:176` | exit 3, even when the correct range is passed |
| `qa-skill skills install` | `install.ts:121` → `manifest.ts:70` | throws a plain `Error` → exit 5 |
| `resolveCompatibleRuntime` | `agents.ts:116` | treats an installed 1.0.0 binary as incompatible |
| `qa-skill skills verify` | `verify.ts:47-50` | a healthy installation reports itself `runtime-incompatible` → exit 1 |
| `readManifest` | `manifest.ts:102,110` | every manifest stamped by 1.0.0 is refused |
| `npm run smoke:package` | `smoke-package-consumer.ts:69` | red, and CI red with it |

Plus 13 places in the documentation that teach the user to run `--range ">=0.1.0 <1.0.0"` — the first command in every SKILL.md preflight and in both READMEs.

**And the current test suite does not catch any of it.** Every installer test resolves a *fake* binary printing `0.1.0` (`tests/installer/runtime-fixture.ts:32,43`), so they stay green after the bump even though the real binary is refused. No test calls `isRuntimeCompatible` directly, and no test touches the `range !== runtimeCompatibility` line.

## Decisions

Each was taken by the user during brainstorming; the reasoning is recorded so it is not relitigated.

1. **Freeze the contract, do not publish yet.** The expensive thing is not being late to npm, it is freezing the *wrong* thing. Release infrastructure is currently zero (no workflow, no tag, `git tag` empty, no `repository` field), so folding it in here would be two projects masquerading as one.
2. **Re-export the types a consumer needs, minus the classes it never constructs.** The code itself already wrote down the reason for re-exporting `PendingObservedExecution` — *"a consumer that handles a field must be able to name its type without reaching into `src/operations/`"* — and then never applied it to the other 14 types. Classes are distinguished by **who constructs them**; see §3.
3. **Align the identity pattern at exactly the two places still out of step.** The same identity must carry the same constraint everywhere, or the promise that it "cannot collide" is only half true. Not extended to `runId` — a timestamp-hex pattern is far stricter than merely forbidding a colon, and it has not been measured against real data.
4. **Move the band to 1.x, keep the style of the gate.** Neither drop the `range !== runtimeCompatibility` line nor add a semver parser: that is pre-existing behaviour, not something 1.0 additionally freezes. Loosening a safety gate immediately before locking semver is the wrong moment.

## What ships

### Group 1 — the compatibility mechanism (first, because every later group runs under the new band)

- `runtimeCompatibility` → `">=1.0.0 <2.0.0"`; regex → `^1\.\d+\.\d+(?:-[0-9A-Za-z.-]+)?$`.
- **Add a test that calls `isRuntimeCompatible` directly**, covering both gating layers: a valid 1.x version, a 0.x version that is now refused, and a range other than the literal (proving the short-circuit line still holds). *No test currently* does this, and that is exactly why the trap could survive.
- **Move the installer fixtures to `1.0.0`** (`runtime-fixture.ts:32,43`, `lifecycle.test.ts:39,50,114`, the `0.1.0`/`0.2.0` lines in `windows-paths.test.ts`). **Without this, the phase ships a test suite that lies** — green while the real binary is refused.
- Fix the 13 hardcoded range sites: `README.md:23`, `docs/README.vi.md:24`, 6 `skills/*/SKILL.md` files, `skills/shared/references/agent-browser-adapters.md:7`, `scripts/smoke-package-consumer.ts:69`, `tests/cli/workflow.test.ts:207`, `tests/installer/windows-paths.test.ts:167` (comment).

Leave `windows-paths.test.ts` using `9.0.0` as its incompatible case — but note that after the band changes, `9.0.0` and `0.x` are refused by the *same* clause, so that case no longer distinguishes "refusing a foreign version" from "refusing its own superseded line".

### Group 2 — the API surface

Add to `src/orchestration/qa-tester.ts` the types a consumer needs in order to use the API but cannot currently name:

`PublicWorkflowMode`, `WorkflowOperationName`, `WorkspaceValidation`, `WorkspaceDiagnostic`, `ReleaseRecommendation`, `ArtifactRecord`, `ExplorationCharter`, `SecretResolver`, `EvidencePolicyLayers`, `TelemetryScrubber`, plus `RetestScenario` and `RetestSource` — these two are currently **not `export`ed at all** (`run-workflow.ts:731,732`), so they must be exported at the source first.

Classes are handled by **who constructs them**, measured from `QaRuntimeRegistry`:

| Class | Treatment | Reason |
|---|---|---|
| `TestDataHookRegistry` | export | a consumer must call `TestDataHookRegistry.fromConfig(...)` to populate `testDataRegistries` |
| `ExternalPermitRegistry` | export | a consumer must `new ExternalPermitRegistry(...)` |
| `RunWorkspace` | **not** exported | appears only in `WorkflowOperationInputMap` — something a consumer reads rather than constructs; exporting it would lock the whole method surface into semver with nobody gaining |

`Browser` needs no treatment: it comes from `@playwright/test`, which a consumer installs itself.

### Group 3 — aligning the identity pattern

| Schema | Version | Fields |
|---|---|---|
| `evidence` | 3.0.0 → 4.0.0 | `subject.testCaseId`, `subject.testCaseRevisionId`, `subject.testCaseInstanceId` |
| `regression-selection` | 1.0.0 → 2.0.0 | `$defs.decision.testCaseId`, `$defs.decision.revisionId`, `$defs.decision.instanceId` |

These are the **only two places** still carrying the identity triple without `^[^:]+$`. `runId` is untouched (strict pattern, unmeasured), `attemptId` untouched, and the remaining 20 schemas untouched.

With a `schemaVersion` literal sweep, as Phase 9 Task 1 did — and the lesson from that one must go into the brief: **a count proves presence, not correctness.** Every site must be checked for having moved to the right new value, not merely counted.

### Group 4 — the bump and the declaration, last

- `package.json:3` and `src/installer/manifest.ts:7` → `"1.0.0"`.
- `tests/cli/core.test.ts:29` currently hardcodes `stdout: "0.3.0\n"` instead of reading `runtimeVersion` — fix it so it needs no hand edit at every later bump.
- **Write into the README a sentence that has never existed: what 1.0 means.** Today no README, no CONTEXT.md, and no ADR says anything about API stability, deprecation, or the supported band. Minimum content: the public API is the names re-exported from `.` plus the CLI contract; everything else is an internal detail and may change in a minor.
- **Widen `smoke:package`.** It currently type-checks exactly **1 of 22** public names and has never imported `./cli`. If 1.0 locks 22 names, then letting the only gate that checks the public surface at the packaging boundary check 1 name is a contradiction. Widen the consumer file to import every public name and the `./cli` subpath as well.

**Recorded plainly because it bears on who decided what:** widening `smoke:package` is a question I raised and that went unanswered before I was told to write the spec. It is in because of the contradiction argued above, not because it was ruled on. It is the easiest item to cut if you want to narrow the phase — cutting it affects no other group.

The bump goes last so every earlier group runs under the new band before the number changes.

## Error handling

No new exit code, no new error code, no new dependency. Group 1 changes the *values* `isRuntimeCompatible` accepts, not the *shape* of the error it produces.

## Testing

TDD; every test proven by mutation; no snapshots; relative imports end in `.js`. The nine-command gate from a deleted `dist/`, floor 90/80/95/90.

Group-specific obligations:

- **Group 1** — the test that calls `isRuntimeCompatible` directly is the centrepiece. Mutation must prove: reverting the regex to `^0\.` reddens the 1.x case, and dropping the short-circuit line reddens the range-other-than-the-literal case.
- **Group 2** — adding type re-exports changes no behaviour, so the evidence lives in the widened `smoke:package` (Group 4), not in a unit test. Say so rather than inventing a fake test.
- **Group 3** — one rejection test per newly patterned field: an id containing a colon must be refused at registration.
- **Group 4** — `--version` must read from `runtimeVersion`, proven by changing that constant and watching the test go red.

**Stage with `git add` BEFORE running `npm run scan:secrets`** — the scanner walks `git ls-files`, and this project has twice recorded a passing scan that was spurious because the file was untracked.

## Out of scope

- Publishing to npm, the release workflow, CHANGELOG, tag convention, provenance, `repository`/`publishConfig`, `prepublishOnly`.
- Extending the pattern to `runId`, `attemptId`, or the remaining 20 schemas.
- Dropping the `range !== runtimeCompatibility` line or adding a real semver parser.
- Exporting `RunWorkspace`, or any class a consumer does not have to construct itself.
- The three doc minors parked since Phase 9: the `projection-model.ts:204` citation in `recovery.md`, the caller count that is off by one in `observed-coverage.ts`, and the leftover "an unrelated batch" sentence in the Testing section of the Phase 9 spec.
- Any new feature.
